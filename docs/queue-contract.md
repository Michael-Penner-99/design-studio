# Queue contract — the protocol between the Vercel app, GitHub, and the local worker

> The Vercel operator app, the GitHub `design-studio` repo, and the polling worker on your Mac all share state through one folder structure. This document is the source of truth.

## Repo layout (the monorepo)

```
design-studio/                          # github.com/Michael-Penner-99/design-studio
├── README.md                           # Top-level (factory + app + worker)
├── CLAUDE.md                           # Orchestrator instructions (factory)
├── .env.example                        # Combined env for factory + worker
├── .claude/                            # Factory subagents
├── sops/                               # Factory SOPs
├── skills/                             # Factory skills
├── templates/                          # Page + section + walkthrough templates
├── recipes/                            # Per-sub-trade recipes
├── quality-gates/                      # QA checklist
├── scripts/                            # Factory + worker scripts
├── docs/                               # Architecture, how-to-run, this file
├── clients/                            # Per-client outputs (gitignored except _deployed.json)
│   └── _deployed.json
├── queue/                              # PENDING JOB SPECS (committed by Vercel app)
│   └── {run-id}.json
├── runs/                               # FINISHED RUN STATUS (committed by worker)
│   └── {run-id}.json
└── web/                                # Vercel operator app (separate deploy target)
    ├── package.json
    ├── next.config.mjs
    ├── app/                            # Next.js App Router
    ├── lib/                            # GitHub client, queue helpers
    └── public/
```

**Why one repo, not three:** message passing happens through git. The Vercel app commits to `queue/`; the worker reads from `queue/` and writes to `runs/`. Three repos would mean three sets of auth, three deploys, three places to keep in sync. One repo is the simplest thing that works.

**Vercel projects deployed from this repo:**
- `factory-actiondesignstudio` — root directory = `web/`. Domain: `factory.actiondesignstudio.com`. Password-protected.
- `{slug}-site` — one per client. Root directory = `clients/{slug}/site/`. Domain: `{slug}.actiondesignstudio.com`. Public.
- `{slug}-sales` — one per client. Root directory = `clients/{slug}/sales/`. Domain: `{slug}-sales.actiondesignstudio.com`. Public, but only Michael shares the URL.

## Run identifier

```
run-{YYYYMMDD}-{HHMMSS}-{4-char-random}
```

Example: `run-20260518-184501-a7f3`

Generated by the Vercel app at submission time.

## Job spec — `queue/{run-id}.json`

Written by the Vercel app when an operator clicks "Run". The worker reads this file to know what to do.

```json
{
  "run_id": "run-20260518-184501-a7f3",
  "submitted_at": "2026-05-18T18:45:01Z",
  "submitted_by": "michael@innovusaccounting.com",
  "mode": "url" | "name-and-reviews",

  "url": "https://example-contractor.com",
  "business_name": "Example HVAC",
  "trade_hint": "hvac",
  "primary_city": "Kansas City, MO",
  "reviews_text": "Pasted reviews if mode=name-and-reviews. Free-form text...",
  "manual_notes": "Optional operator notes, prepended to brief.md body.",

  "options": {
    "skip_deploy": false,
    "force_archetype": null,
    "ai_image_provider": "openai"
  }
}
```

Field rules:
- `mode` is the discriminator. Required.
- If `mode: "url"`: `url` is required. `business_name`, `primary_city`, `reviews_text` are ignored.
- If `mode: "name-and-reviews"`: `business_name`, `trade_hint`, `primary_city`, `reviews_text` are required. `url` is ignored.
- `options` is optional throughout. Defaults: skip_deploy=false, force_archetype=null, ai_image_provider="openai".

## Status file — `runs/{run-id}.json`

Written by the worker at submission acknowledgment, updated after each phase, finalized when the run completes or halts.

```json
{
  "run_id": "run-20260518-184501-a7f3",
  "slug": "example-hvac",
  "mode": "url",
  "url": "https://example-contractor.com",
  "started_at": "2026-05-18T18:45:30Z",
  "updated_at": "2026-05-18T19:14:22Z",
  "status": "running" | "completed" | "halted",
  "current_phase": 5,
  "phases": {
    "1": { "name": "Discovery",       "status": "completed", "started_at": "...", "completed_at": "..." },
    "2": { "name": "Capture",         "status": "completed", "started_at": "...", "completed_at": "..." },
    "3": { "name": "Brand DNA",       "status": "completed", "started_at": "...", "completed_at": "..." },
    "4": { "name": "Strategy",        "status": "completed", "started_at": "...", "completed_at": "..." },
    "5": { "name": "Build",           "status": "running",   "started_at": "..." },
    "6": { "name": "Quality",         "status": "pending" },
    "7": { "name": "Sales-Ready",     "status": "pending" },
    "8": { "name": "Deploy & Handoff","status": "pending" }
  },
  "outputs": {
    "site_url": null,
    "sales_walkthrough_url": null,
    "proposal_pdf_path": null
  },
  "halt_reason": null,
  "halt_phase": null
}
```

When `status: completed`:
- `outputs.site_url` = e.g. `https://example-hvac.actiondesignstudio.com`
- `outputs.sales_walkthrough_url` = e.g. `https://example-hvac-sales.actiondesignstudio.com`
- `outputs.proposal_pdf_path` = e.g. `clients/example-hvac/proposal/proposal.pdf`

When `status: halted`:
- `halt_reason` = short string from `clients/{slug}/halt.md`
- `halt_phase` = phase number where halt occurred

## Worker poll loop (high level)

```
every 30 seconds:
  git pull --rebase
  list queue/*.json sorted by submitted_at
  for each spec not present in runs/:
    write initial status to runs/{run-id}.json (status: running, current_phase: 1)
    derive slug from spec
    scaffold clients/{slug}/ (URL mode: scripts/new-client.sh, name+reviews mode: scripts/new-client-from-name.sh)
    drive Claude Code through the 8 phases (using the trigger phrase that matches the mode)
    update runs/{run-id}.json after each phase
    when complete or halted: commit + push runs/{run-id}.json
```

The Vercel app reads `runs/` on every page load — fresh status without needing a database.

## Concurrency

V1 assumes ONE worker on ONE Mac running ONE job at a time. The worker takes a job by writing its initial status file; this acts as a lock. If a second worker ever ran, it would skip jobs that already have a status file. No race conditions in practice because there's only one operator.

## Failure & retries

If the worker crashes mid-run:
- The status file is left as-is (`status: running` with a `current_phase`).
- On worker restart, it scans `runs/` for any `status: running` files older than 30 minutes and:
  - Marks them `status: halted`, `halt_reason: "worker-crashed-or-restarted"`.
  - Leaves `clients/{slug}/` intact for manual recovery via `resume {slug}` in Claude Code.

## Security notes

- The `queue/` and `runs/` folders are public in the GitHub repo (the repo is private, but the Vercel app needs read access). No secrets ever go in these files — only run metadata.
- API keys (Google Places, Vercel, OpenAI) live only in `.env` on Michael's Mac and as Vercel project env vars. They never enter git.
- The Vercel operator app is password-protected via Vercel's built-in Password Protection (Settings → Deployment Protection → Password). One password, set in the dashboard.
